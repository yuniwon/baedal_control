# 통합메뉴 워크스페이스 UI 재설계

- 문서 상태: 구현 전 설계 확정안
- 작성일: 2026-07-26
- 대상: 기존 `Delivery Menu Sync` Electron 앱의 활성 통합메뉴 관리 경험

## 1. 목표

초기 통합메뉴 구성을 마친 뒤에도 사용자가 같은 수준의 단순한 화면에서 메뉴를 찾고, 수정하고, 플랫폼별 차이를 확인하고, 검토할 수 있게 한다.

핵심 성공 기준은 다음과 같다.

- 120개 이상의 메뉴가 있어도 원하는 메뉴를 빠르게 찾을 수 있다.
- 평소에는 통합메뉴만 보이고 플랫폼 원본은 필요할 때만 펼친다.
- 메뉴 하나를 수정할 때 다른 메뉴나 플랫폼 원본을 실수로 건드리지 않는다.
- 저장 전 변경 내용과 영향을 받는 플랫폼을 이해할 수 있다.
- 기존 운영 매장도 현재 메뉴를 보존한 채 통합메뉴를 다시 구성할 수 있다.
- 백업, 검토, 플랫폼 반영 같은 후속 단계가 같은 정보구조 안에 자연스럽게 들어간다.

## 2. 확인된 현재 문제

현재 화면은 기능은 많지만 작업 단위가 분리되지 않았다.

- `MenuPage`가 목록 구성, 플랫폼 원본 결합, 검색, 필터, 저장, 추가, 삭제를 한 파일에서 담당한다.
- 모든 메뉴 행에 입력칸이 노출되고 입력할 때마다 저장 요청이 발생한다.
- `새 메뉴`를 누르면 미완성 메뉴가 즉시 DB에 생성된다.
- 필터가 여러 개의 큰 버튼으로 나열되어 메뉴 목록보다 먼저 시선을 차지한다.
- 카테고리별 전체 테이블이 한 번에 펼쳐져 120개 규모에서 탐색 비용이 크다.
- 원본 상세는 접을 수 있지만 메뉴 편집과 플랫폼 비교의 위계가 명확하지 않다.
- 저장 성공, 실패, 미저장 변경, 화면 이탈 경고가 없다.
- 초기 온보딩 화면은 `collecting` 작업공간만 볼 수 있어 `active / legacy` 매장은 재구성할 방법이 없다.
- 홈, 메뉴, 옵션, 연결, 검토의 책임이 일부 중복된다.

## 3. 검토한 접근 방식

### A. 현재 테이블의 시각적 정리만 수행

개발량은 작지만 모든 행의 인라인 편집, 즉시 저장, 긴 목록 문제를 그대로 남긴다. 핵심 작업 흐름이 바뀌지 않으므로 채택하지 않는다.

### B. 각 배달 플랫폼 관리화면을 앱 안에 각각 복제

사용자에게 익숙할 수 있지만 플랫폼별 차이를 다시 학습해야 하고 통합메뉴의 의미가 약해진다. 플랫폼이 늘어날 때 화면도 계속 늘어나므로 채택하지 않는다.

### C. 통합메뉴 중심 목록-상세 워크스페이스

통합메뉴를 유일한 기본 작업 단위로 두고, 플랫폼 정보는 선택한 메뉴의 비교 자료로만 제공한다. 온보딩의 단순한 톤과 기존 데이터 구조를 함께 유지할 수 있으므로 이 방식을 채택한다.

## 4. 정보구조

기본 내비게이션은 네 항목으로 정리한다.

1. `홈`: 오늘 필요한 작업, 연결 상태, 최근 결과
2. `통합메뉴`: 메뉴와 옵션을 찾고 편집하는 주 작업 공간
3. `검토함`: 누락, 가격 차이, 중복 옵션, 외부 변경 판단
4. `가져오기`: 플랫폼 연결과 최신 원본 읽기

고급 기능에는 다음을 둔다.

- `플랫폼 연결`: 자동 연결 후보와 수동 매핑
- `기록`: 가져오기, 변경 계획, 실행 결과
- `백업 및 내보내기`: Phase 3에서 활성화

현재의 `메뉴`와 `옵션`은 별도 제품 영역이 아니라 `통합메뉴` 안의 보기 전환으로 합친다. 데이터 구조와 기존 페이지 로직은 유지하면서 진입점만 통합한다.

## 5. 통합메뉴 화면

### 5.1 기본 구조

넓은 데스크톱 창에서는 다음 세 영역을 사용한다.

- 왼쪽: 카테고리와 저장된 상태 필터
- 가운데: 검색 가능한 통합메뉴 목록
- 오른쪽: 선택한 메뉴의 상세 편집 패널

창 폭이 좁으면 상세 패널은 오른쪽 슬라이드 패널로 열린다. 선택 전에는 가운데 목록이 넓게 보인다.

### 5.2 목록

한 메뉴 행은 다음 정보만 기본 노출한다.

- 메뉴명
- 대표 가격 또는 `M 19,900 · L 22,900` 같은 짧은 가격 요약
- 연결된 플랫폼 수
- `검토 2`, `플랫폼 누락 1`, `미저장 변경` 같은 필요한 상태
- 관리 대상 여부

원본 ID, 긴 옵션 목록, 마지막 수집 설명은 목록에서 숨긴다. 카테고리는 접을 수 있는 거대한 테이블이 아니라 왼쪽 탐색과 목록의 짧은 구분선으로 사용한다.

검색은 메뉴명, 플랫폼 메뉴명, 가격, 옵션명까지 한 입력창에서 처리한다. 기본 필터는 `전체 / 검토 필요 / 플랫폼 누락 / 관리 제외` 네 개만 두고 나머지는 `필터` 팝오버에 넣는다.

### 5.3 상세 편집

메뉴를 선택하면 오른쪽 패널에 다음 순서로 표시한다.

1. 메뉴명과 관리 상태
2. 기준 가격 및 사이즈·채널별 가격
3. 옵션 구성 요약
4. 플랫폼별 연결·가격·노출 차이
5. 고급 원본 정보

입력은 로컬 편집 초안에만 반영한다. `저장`을 눌렀을 때 한 번만 DB에 저장하고, 저장 전 화면 이탈에는 확인을 표시한다. 저장 실패는 패널 안에서 복구 가능한 오류로 보여준다.

`삭제`는 기본 동작으로 사용하지 않는다. 먼저 `관리 제외`를 제공하고, 플랫폼 연결이 전혀 없는 메뉴만 고급 동작에서 영구 삭제할 수 있다.

### 5.4 새 메뉴

`새 메뉴`는 즉시 빈 레코드를 만들지 않는다. 작은 작성 패널에서 최소 필수값을 완성한 뒤 저장한다.

- 메뉴명
- 카테고리
- 기준 가격 또는 가격 변형
- 관리 대상 여부

플랫폼 배포 선택은 Phase 4의 안전한 반영 계획이 준비된 뒤 추가한다.

## 6. 플랫폼 비교

각 플랫폼별 관리화면의 구성 방식은 앱 화면을 복제하는 용도가 아니라 비교 필드와 제약 설명에만 사용한다.

플랫폼 비교 행에는 다음을 표시한다.

- 연결 상태: 연결됨 / 없음 / 확인 필요
- 플랫폼 메뉴명
- 현재 가격 요약
- 통합메뉴와의 차이
- 해당 플랫폼에서 지원하지 않는 필드
- 마지막으로 읽은 시각

의도된 차이는 `이 차이 유지`로 기록하고, 실수 가능성이 높은 차이는 `검토함에서 확인`으로 연결한다. 원본 JSON이나 내부 ID는 고급 정보에서만 제공한다.

## 7. 검토함

홈에는 검토 개수와 가장 중요한 3개 그룹만 보여준다. 실제 판단은 독립된 `검토함`에서 수행한다.

검토함의 기본 그룹은 다음과 같다.

- 다른 플랫폼에 없는 메뉴
- 플랫폼별 가격 차이
- 중복 또는 파편화된 옵션
- 새로 발견된 원본 메뉴
- 플랫폼에서 직접 바뀐 값
- 플랫폼 기능 제약으로 손실되는 값

한 번에 한 그룹을 열고, 영향 메뉴와 추천 근거를 본 뒤 `통합메뉴에 반영 / 플랫폼에 추가할 후보 / 의도된 차이 / 관리 제외 / 나중에 결정` 중 하나를 선택한다. 여러 범위에 적용하는 기능은 고급 선택으로 유지한다.

## 8. 기존 운영 매장 재구성

`active / legacy` 작업공간에는 홈과 통합메뉴 상단에 `초기 통합메뉴 재정비 필요` 상태를 표시한다. 사용자가 선택하면 현재 활성 메뉴를 변경하지 않고 별도 재구성 초안을 만든다.

흐름은 다음과 같다.

1. 최신 플랫폼 원본 완전성 확인
2. 기준 플랫폼 또는 빈 시작 선택
3. 새 통합메뉴 초안 검토
4. 현재 활성 메뉴와 새 초안 비교
5. 자동 복구 지점 생성
6. 사용자 최종 확인 후 새 버전 활성화

초안을 취소하면 현재 메뉴에는 아무 변화가 없어야 한다. 자동 복구 지점이 만들어지기 전에는 활성화를 허용하지 않는다. 따라서 재구성 활성화는 Phase 3 백업 코어와 연결한다.

## 9. 후속 단계와의 관계

현재 로드맵 상태는 다음과 같다.

- Phase 1 통합메뉴 온보딩과 예외 판단 기반: 기능 구현 완료, 기존 매장 재진입 UX 보완 필요
- Phase 2 플랫폼 플러그인과 세션: 기능 구현 완료
- Phase 2 후속 쿠팡 Chrome 비밀번호 관리자 로그인: 기능 구현 완료
- Phase 2.5 통합메뉴 워크스페이스 UI 재설계: 신규 작업
- Phase 3 백업·복원·CSV·PDF: 미구현
- Phase 4 안전한 다중 플랫폼 반영: 미구현

UI 재설계의 목록·상세·검토함은 Phase 3보다 먼저 구현할 수 있다. 기존 매장 재구성의 최종 활성화는 Phase 3의 자동 복구 지점이 준비된 뒤 연다. Phase 4는 상세 편집 패널의 `변경 확인`과 기록 화면을 재사용한다.

## 10. 접근성 및 안전 기준

- 모든 아이콘 버튼에는 텍스트 이름을 제공한다.
- 색만으로 상태를 구분하지 않고 문구와 모양을 함께 사용한다.
- 키보드로 목록 이동, 상세 열기, 저장, 닫기가 가능해야 한다.
- 상세 패널이 열리면 제목과 현재 선택 메뉴를 보조기술에 알린다.
- 저장 중 중복 저장을 막고 결과를 `role=status` 또는 `role=alert`로 알린다.
- 최소 1024px 폭에서 가로 스크롤 없이 핵심 작업이 가능해야 한다.
- 실제 플랫폼 쓰기는 Phase 4의 승인 화면 전에는 호출하지 않는다.

## 11. 감사 한계

현재 실행 중인 Electron 창을 이 작업 환경의 앱 브라우저로 직접 캡처할 수 없어 정식 스크린샷 기반 감사는 수행하지 못했다. 이 설계는 현재 렌더러 코드, 테스트, 온보딩 콘셉트 이미지, 로컬 DB의 메뉴 규모를 근거로 작성했다. 구현 첫 작업에서 실제 앱 스크린샷을 기준선으로 남기고 동일 작업 흐름을 다시 확인해야 한다.
