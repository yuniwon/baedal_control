# 배달앱 메뉴 동기화 로컬 앱 설계서

- 작성일: 2026-04-12
- 대상 사용자: 배달앱 사장님 1인, 매장 1개 운영
- 문서 목적: MVP 범위와 제품/기술 구조를 고정하고, 다음 단계 구현 계획의 기준으로 사용

## 1. 문제 정의

사용자는 여러 배달앱 사장님 사이트에 각각 로그인해 메뉴명과 가격을 수작업으로 수정하고 있다.  
이 작업은 반복적이고 시간이 오래 걸리며, 한 플랫폼만 빠뜨려도 실제 판매 정보가 불일치할 수 있다.

이 제품의 목표는 다음과 같다.

1. 사장님이 한 곳에서 메뉴명과 가격을 수정할 수 있게 한다.
2. `전체 반영` 한 번으로 여러 플랫폼에 변경 내용을 순차 반영한다.
3. 반영 전 미리보기, 반영 후 실행 결과 기록을 제공해 불안감을 줄인다.

## 2. 제품 한줄 정의

윈도우 PC에서 실행되는 로컬 앱으로, 메뉴 기준 데이터를 한 곳에서 관리하고 배민/쿠팡이츠/땡겨요 사장님 사이트에 자동 로그인하여 메뉴명과 가격을 동기화한다.

## 3. 목표와 성공 기준

### 목표

- 메뉴명과 가격 수정 작업을 단일 앱으로 통합
- 플랫폼별 반복 로그인/수정 시간을 크게 단축
- 잘못 반영될 위험을 미리보기와 로그로 통제

### MVP 성공 기준

- 사장님이 앱 안에서 메뉴명/가격을 수정할 수 있다.
- `전체 반영` 실행 시 배민, 쿠팡이츠, 땡겨요에 대해 변경분만 반영할 수 있다.
- 반영 전 변경 예정 내용을 확인할 수 있다.
- 플랫폼별 성공/실패/확인 필요 상태를 분리해 볼 수 있다.
- 실패한 플랫폼만 다시 시도할 수 있다.

## 4. 범위

### MVP 포함

- 윈도우 전용 로컬 앱
- 매장 1개 관리
- 메뉴명
- 기본 가격
- 내부적으로 플랫폼별 예외값을 담을 수 있는 데이터 구조
- 배민/쿠팡이츠/땡겨요 연동
- 플랫폼 계정 암호화 저장
- 플랫폼 메뉴 읽어오기
- 최초 1회 자동 매칭 + 사용자 확인
- 반영 전 미리보기
- 전체 반영
- 플랫폼별 재시도
- 실행 로그 저장

### MVP 제외

- 옵션
- 설명
- 이미지
- 여러 매장/지점 관리
- 모바일 앱
- 클라우드 계정 보관
- 자동 스케줄 반영
- 배달특급/요기요/네이버주문 연동
- AI 기반 메뉴 추천/보정

## 5. 플랫폼 전략

### 1차 연동 대상

- 배달의민족
- 쿠팡이츠
- 땡겨요

### 향후 연동 후보

- 배달특급
- 요기요
- 네이버주문

### 구현 원칙

1. 공개 메뉴관리 API가 확인되지 않은 플랫폼은 브라우저 자동화 기반으로 구현한다.
2. 각 플랫폼은 독립 어댑터로 분리한다.
3. 특정 플랫폼 화면이 바뀌어도 다른 플랫폼은 영향받지 않게 한다.
4. 즉시 수정이 불가능한 항목이나 별도 요청 절차가 필요한 기능은 MVP에서 제외한다.

## 6. 핵심 사용자 흐름

### 최초 설정

1. 앱 설치
2. 플랫폼 계정 입력 및 저장
3. 각 플랫폼에서 현재 메뉴 읽기
4. 앱이 메뉴를 자동 매칭
5. 사장님이 매칭 결과 검수 후 확정

### 일상 사용

1. 메뉴 관리 화면에서 메뉴명 또는 가격 수정
2. 변경 내용이 로컬 DB에 저장
3. 대시보드 또는 메뉴 화면에서 `전체 반영` 클릭
4. 반영 전 미리보기에서 플랫폼별 변경 예정 내용 확인
5. 실행 승인
6. 배민 -> 쿠팡이츠 -> 땡겨요 순서로 자동 로그인 및 반영
7. 플랫폼별 결과 확인
8. 실패 시 실패 플랫폼만 재시도

## 7. 정보 구조와 화면 설계

### 7.1 대시보드

- 마지막 반영 시간
- 플랫폼별 연결 상태
- 최근 실행 결과
- `전체 반영` 버튼
- 주의 메시지: 영업 중 반영 리스크 또는 권장 시간

### 7.2 메뉴 관리

- 메뉴 목록 테이블
- 컬럼: 메뉴명, 기본 가격, 변경 여부, 마지막 반영 상태
- 검색/정렬
- `플랫폼별 다르게 설정` 접기/펼치기
- MVP 기본값은 공통 메뉴명/공통 가격

### 7.3 메뉴 연결 확인

- 앱 기준 메뉴와 플랫폼 메뉴의 연결 상태 표시
- 자동 매칭 결과 검토
- 사용자가 수동으로 연결 수정 가능
- 확정 후 재사용

### 7.4 반영 결과 / 실행 기록

- 실행 시간
- 플랫폼별 상태: 성공 / 실패 / 확인 필요
- 실패 원인
- 재시도 버튼
- 필요 시 캡처 또는 상세 로그 접근

## 8. UX 원칙

1. 저장과 반영을 분리한다.
2. 반영 전 반드시 변경 미리보기를 보여준다.
3. 평소에는 단순한 공통값 UI만 보여주고, 플랫폼별 예외는 접어 둔다.
4. 실패를 전체 실패로 뭉개지 않고 플랫폼 단위로 분리한다.
5. 자동화 결과에 대한 증거를 남긴다.

## 9. 기술 구조

### 9.1 클라이언트 앱

- 형태: 윈도우 데스크톱 앱
- 권장 스택: Electron
- 이유:
  - Playwright와 결합이 쉽다.
  - 로컬 파일/DB/운영체제 자격 증명 저장소 접근이 수월하다.
  - MVP 기준 생산성과 유지보수성이 높다.

### 9.2 자동화 엔진

- 권장 도구: Playwright
- 역할:
  - 로그인
  - 메뉴 목록 읽기
  - 특정 메뉴 탐색
  - 메뉴명/가격 수정
  - 저장 결과 확인

### 9.3 로컬 데이터 저장

- 권장 DB: SQLite
- 저장 대상:
  - 메뉴 기준 데이터
  - 플랫폼별 메뉴 매핑
  - 변경 이력
  - 실행 로그
  - 설정 값

### 9.4 계정 보관

- 플랫폼 아이디/비밀번호는 로컬에서만 보관
- 권장 방식:
  - Windows Credential Manager 또는
  - Windows DPAPI 기반 암호화 저장

### 9.5 플랫폼 어댑터 구조

각 플랫폼 어댑터는 공통 인터페이스를 구현한다.

- `login()`
- `fetchMenus()`
- `updateMenuName()`
- `updateMenuPrice()`
- `verifyChanges()`

이 구조를 통해 플랫폼 추가 시 앱 공통 영역은 건드리지 않고 새 어댑터만 붙일 수 있어야 한다.

## 11. 변경 비교와 반영 규칙

1. 앱은 기준 데이터와 각 플랫폼의 마지막 확인값을 비교한다.
2. 변경되지 않은 메뉴는 건너뛴다.
3. 메뉴명과 가격만 반영 대상에 포함한다.
4. 플랫폼별 예외값이 있으면 기본값보다 우선한다.
5. 메뉴가 매핑되지 않은 경우 자동 반영하지 않고 `확인 필요`로 표시한다.

## 12. 오류 및 예외 처리

플랫폼별로 아래 오류를 구분해 저장하고 표시한다.

- 로그인 실패
- 메뉴 목록 진입 실패
- 메뉴 탐색 실패
- 저장 버튼 실행 실패
- 변경 결과 검증 실패
- 예기치 않은 팝업/레이어 발생
- 세션 만료

오류 처리 원칙:

1. 한 플랫폼 실패가 다른 플랫폼 실행을 막지 않는다.
2. 실패 플랫폼만 재시도할 수 있어야 한다.
3. 자동화가 확실히 끝났는지 확인되지 않으면 `성공`이 아니라 `확인 필요`로 처리한다.
4. 사용자에게는 기술 용어보다 행동 지침 중심으로 보여준다.

## 13. 보안 및 운영 원칙

1. 계정 정보는 외부 서버에 저장하지 않는다.
2. 실행 로그에는 비밀번호나 민감한 토큰을 남기지 않는다.
3. 앱 자체 잠금 PIN 또는 윈도우 사용자 인증을 후속 기능으로 고려한다.
4. 플랫폼 약관 및 인증 정책 변화에 따라 로그인 정책을 재검토할 수 있게 한다.

## 18. 외부 사실 확인 메모

2026-04-12 기준 공개 자료 확인 결과, MVP 대상 플랫폼에 대해 공개된 메뉴관리 API는 바로 확인되지 않았다.  
따라서 1차 구현은 브라우저 자동화 전제로 설계한다.  
배달특급은 PAYCO 스마트오더 계열 사이트와 연결되며, 향후 대상 플랫폼 추가 시 공통 백엔드 여부를 따로 분석한다.
