# 통합 메뉴 원본·예외·플랫폼 확장·복구 기반 설계

- 작성일: 2026-07-25
- 대상 제품: Delivery Menu Sync
- 관련 문서:
  - `docs/platform-capability-matrix.md`
  - `docs/platform-capability-matrix.json`
  - `docs/superpowers/specs/2026-07-21-six-platform-catalog-ingestion-design.md`
  - `docs/superpowers/specs/2026-04-13-unified-menu-management-information-architecture-design.md`
- 문서 목적: 초기 통합 메뉴 구성부터 예외 판단, 플랫폼 추가, 인증 복구, 외부 백업까지의 상위 제품·기술 결정을 고정한다.

## 1. 한줄 정의

매장마다 선택한 플랫폼 또는 빈 카탈로그에서 최초 통합 메뉴를 만들고, 확정 이후에는 통합 메뉴를 원본으로 삼아 각 플랫폼의 차이를 설명·기억·안전하게 반영하는 확장 가능한 관리 워크스페이스를 만든다.

## 2. 해결하려는 문제

기존 사업자의 플랫폼 데이터는 이미 서로 다르다.

- 특정 플랫폼에만 없는 메뉴가 누락인지 의도적인 제외인지 알 수 없다.
- 같은 메뉴의 사이즈별 가격 차이가 실수인지 플랫폼 전략인지 알 수 없다.
- 실제로 같은 옵션이 여러 그룹으로 파편화되어 있다.
- 비노출·판매 종료·삭제 불가 메뉴가 정상 메뉴와 섞여 있다.
- 플랫폼마다 지원하는 가격, 옵션, 이미지, 상태, 프로모션 구조가 다르다.
- 플랫폼 관리화면에서 직접 수정한 값과 통합 메뉴의 변경이 충돌할 수 있다.
- 로그인 세션이 만료되거나 자동화 브라우저가 거절되면 수집이 중단된다.
- 앱이나 로컬 DB가 손상되면 통합 메뉴와 판단 이력을 잃을 수 있다.

사용자에게 이 모든 원본을 그대로 펼쳐 보이면 통합 관리가 개별 관리보다 더 복잡해진다. 제품은 자동으로 정리할 수 있는 항목을 먼저 처리하고, 의도를 알아야 하는 예외만 짧고 일관된 질문으로 보여줘야 한다.

## 3. 범위와 비범위

### 포함

- 매장별 초기 기준 플랫폼 선택
- 빈 통합 메뉴에서 시작하는 경로
- 초기 통합 메뉴 미리보기와 버전 1 확정
- 확정 이후 통합 메뉴를 원본으로 사용하는 규칙
- 플랫폼 원본 스냅샷과 통합 메뉴의 분리
- 메뉴 누락, 가격 차이, 옵션 파편화, 노이즈 후보 탐지
- 사용자의 의도와 예외 결정을 기억하는 모델
- 외부 직접 수정과 통합 메뉴 변경의 충돌 처리
- 플랫폼 플러그인과 기능 제약 계약
- 세션 재사용, 자동 로그인, 사용자 인증 개입 상태 머신
- 외부 백업, 복원, 인쇄·내보내기 원칙
- 플랫폼 반영 전후의 검증과 부분 실패 처리

### 초기 구현에서 제외

- 여러 직원의 역할·승인 권한
- 여러 매장을 한 번에 편집하는 UI
- POS 연동
- 매출 기반 메뉴·가격 추천
- 프로모션 자동 발행
- 백그라운드 상시 동기화
- CAPTCHA, OTP, QR 인증의 우회

제외 항목도 스키마와 인터페이스 확장을 막지 않도록 경계를 둔다.

## 4. 핵심 용어

- `플랫폼 원본`: 플랫폼에서 읽어 보존한 메뉴·옵션·연결 데이터. 통합 메뉴 확정 과정에서 임의 수정하지 않는다.
- `초기 기준 플랫폼`: 해당 매장의 통합 메뉴 버전 1을 만드는 출발점. 서비스 전체의 전역 기준이 아니다.
- `통합 메뉴`: 최초 설정 완료 후 사용자가 책임지고 수정하는 기준 데이터.
- `플랫폼 게시물`: 한 플랫폼에 실제로 존재하는 메뉴·옵션 레코드.
- `변환 계획`: 통합 메뉴를 플랫폼 기능 제약에 맞춰 표현한 쓰기 전 계획.
- `예외 후보`: 시스템이 차이를 발견했지만 의도를 확정할 수 없는 항목.
- `의도 규칙`: 사용자가 차이를 정상으로 인정하거나 처리 방법을 정한 기록.
- `외부 변경`: 마지막 정상 수집 이후 플랫폼 관리화면에서 직접 바뀐 값.
- `복구 스냅샷`: 통합 메뉴와 연결·의도·이력을 복원할 수 있는 버전 데이터.

## 5. 확정된 제품 결정

### 5.1 초기 기준은 매장별로 선택한다

사용자는 최초 설정에서 다음 중 하나를 선택한다.

- 배민을 초기 기준으로 사용
- 요기요를 초기 기준으로 사용
- 쿠팡이츠를 초기 기준으로 사용
- 땡겨요를 초기 기준으로 사용
- 배달특급을 초기 기준으로 사용
- 네이버주문을 초기 기준으로 사용
- 빈 통합 메뉴에서 직접 시작

연결되었고 메뉴 원본 수집이 `complete`인 플랫폼만 기준 후보가 될 수 있다. 특정 플랫폼이 서비스 전체의 영구 기준이라는 전역 플래그는 두지 않는다.

### 5.2 기준 플랫폼은 최초 구성에만 사용한다

초기 기준 플랫폼으로 통합 메뉴 초안을 만든 뒤 다른 플랫폼의 메뉴를 비교한다. 사용자가 검토를 끝내고 `통합 메뉴 버전 1`을 확정하면 이후 원본은 통합 메뉴다.

- 기준 플랫폼에서 나중에 직접 수정된 값도 외부 변경으로 처리한다.
- 기준 플랫폼이라는 이유로 통합 메뉴를 자동 덮어쓰지 않는다.
- 기준 플랫폼 변경은 새 최초 설정이 아니라 명시적인 재구성 작업이다.

### 5.3 플랫폼 원본 수집과 통합 메뉴 생성은 분리한다

현재 구현처럼 플랫폼을 가져오는 즉시 새 통합 메뉴와 확정 매핑을 생성하지 않는다.

```text
플랫폼 수집
  -> 원본 스냅샷 저장
  -> 완전성 검증
  -> 초기 기준 선택
  -> 통합 메뉴 초안 생성
  -> 다른 플랫폼 후보 연결
  -> 예외 검토
  -> 통합 메뉴 v1 확정
```

기존 데이터가 있는 설치는 마이그레이션 시 현재 통합 메뉴를 활성 버전으로 보존한다.

### 5.4 삭제와 정보 손실은 자동 실행하지 않는다

- 플랫폼 원본 행을 자동 물리 삭제하지 않는다.
- 통합 메뉴는 먼저 `관리 제외` 또는 `보관` 상태로 전환한다.
- 플랫폼 메뉴 삭제·옵션 그룹 삭제·옵션 재연결은 별도 정리 계획으로 분리한다.
- `LOSSY`, `UNSUPPORTED`, `UNVERIFIED` 변환이 포함된 쓰기는 기본 차단한다.
- 사용자가 승인한 손실 규칙만 지정한 범위에서 재사용한다.

### 5.5 플랫폼별 차이는 오류가 아니라 의도일 수 있다

모든 차이는 다음 중 하나의 상태를 갖는다.

- `unknown`: 아직 의도를 모름
- `intentional`: 의도적으로 유지
- `temporary`: 기간이 있는 차이
- `mistake`: 수정할 오류로 판단
- `deferred`: 이번에는 판단을 미룸

사용자 결정은 메뉴 하나, 플랫폼 하나, 카테고리, 필드, 매장 전체 중 명시된 범위에만 적용한다.

### 5.6 외부 변경은 자동 흡수하거나 덮어쓰지 않는다

동기화 직전 플랫폼을 다시 읽어 세 값을 비교한다.

1. 마지막 정상 수집값
2. 현재 통합 메뉴값
3. 현재 플랫폼값

- 통합 메뉴만 변경: 플랫폼 반영 후보
- 플랫폼만 변경: 외부 변경 검토 후보
- 양쪽 모두 같은 방향으로 변경: 자동 정합 가능
- 양쪽이 다르게 변경: 충돌로 차단

### 5.7 옵션 통합과 플랫폼 물리 구조를 분리한다

실제로 같은 옵션은 통합 모델에서 하나의 논리 옵션 그룹으로 묶을 수 있다. 플랫폼에서 여러 그룹으로 나뉘어 있는 경우 초기에는 물리 그룹을 삭제·재연결하지 않고 같은 변경을 각 그룹에 투영한다.

다음 값이 모두 같을 때만 자동 병합 후보가 된다.

- 정규화한 그룹명
- 필수 여부와 최소·최대 선택 수
- 정규화한 옵션 항목명과 가격

연결 메뉴 목록만 다른 경우는 통합 후보지만, 선택 규칙이나 항목 가격이 다르면 충돌 후보로 남긴다.

## 6. 통합 메뉴 모델

통합 모델은 다음 엔터티를 분리한다.

- 카테고리
- 상품
- 가격 변형: 사이즈, 용량, 인분 등
- 채널 가격: 배달, 포장·픽업, 매장식사
- 논리 옵션 그룹
- 옵션 항목
- 메뉴와 옵션 그룹 연결
- 이미지 원본과 플랫폼 파생본
- 판매·노출·품절·예약 상태
- 프로모션
- 플랫폼 게시물과 연결

메뉴명 안에 포함된 `M`, `L`, `1.25L` 같은 문자열만으로 상품과 변형을 영구 확정하지 않는다. 시스템은 후보를 제안하고 사용자가 확정한 구조를 보존한다.

## 7. 예외 탐지와 표시

### 7.1 예외 종류

- `missing_on_platform`: 통합 메뉴가 특정 플랫폼에 없음
- `unmatched_platform_menu`: 특정 플랫폼에만 있는 메뉴
- `price_outlier`: 같은 변형의 가격이 한 플랫폼에서만 벗어남
- `price_policy_pattern`: 플랫폼 전체에 일정한 가산·비율 패턴이 있음
- `variant_shape_conflict`: 사이즈·채널 가격 구조가 다름
- `duplicate_option_group`: 동일한 옵션 그룹이 파편화됨
- `option_shape_conflict`: 이름은 같지만 선택 규칙이나 항목이 다름
- `legacy_noise_candidate`: 비노출·오래된·중복·연결 없는 원본 후보
- `external_drift`: 플랫폼에서 직접 변경됨
- `lossy_projection`: 플랫폼 기능 제약 때문에 정보 손실이 발생함
- `authentication_required`: 사용자 인증 없이는 최신 상태를 확인할 수 없음

### 7.2 자동화 수준

- `auto_resolved`: 확실한 정규화. 결과 요약만 표시한다.
- `recommended`: 근거가 충분한 추천. 일괄 승인할 수 있다.
- `decision_required`: 의도 확인 없이는 진행하지 않는다.
- `blocked`: 인증, 기능 제약, 데이터 불완전성 때문에 실행할 수 없다.

### 7.3 사용자 질문 형식

질문은 플랫폼 화면 구조가 아니라 운영 결정을 기준으로 표현한다.

```text
쿠팡이츠에만 '킹쉬림프'가 없습니다.
다른 3개 플랫폼에서는 판매 중이며 메뉴 구성과 가격 변형이 일치합니다.
추천: 쿠팡이츠에 추가

[추가] [의도적으로 제외] [이번에는 건너뛰기]
```

각 결정에는 `이번만 적용`과 `앞으로 같은 경우에도 적용` 범위를 제공한다.

## 8. 의도 규칙 모델

의도 규칙은 최소한 다음 값을 가진다.

- 규칙 ID
- 매장 또는 워크스페이스 ID
- 예외 종류
- 적용 범위: 엔터티, 플랫폼, 카테고리, 필드, 매장 전체
- 대상 메뉴·옵션·플랫폼 식별자
- 해결 방식
- 사람이 읽는 이유
- 생성자와 생성 시각
- 만료 시각
- 활성 여부

자동 수집은 활성 의도 규칙을 덮어쓰지 않는다. 만료된 규칙은 다시 검토 대상으로 전환한다.

## 9. 플랫폼 플러그인 경계

핵심 엔진은 플랫폼 코드별 조건문을 갖지 않고 등록된 플러그인을 사용한다.

```ts
interface PlatformPlugin {
  metadata: PlatformMetadata
  capabilities: PlatformCapabilityManifest
  auth: PlatformAuthDriver
  reader: PlatformCatalogReader
  projector: PlatformCatalogProjector
  writer?: PlatformCatalogWriter
  verifier: PlatformWriteVerifier
}
```

각 플러그인은 다음 책임을 갖는다.

- 공식 관리 사이트와 매장 식별
- 인증 전략과 사용자 개입 조건
- 원본 수집과 완전성 증명
- 통합 메뉴를 플랫폼 모델로 변환
- 지원하지 않는 필드와 손실 정보 보고
- 승인된 변경만 적용
- 반영 후 다시 읽어 결과 검증

`docs/platform-capability-matrix.json`은 제약 근거와 제품 판단의 기준이다. 런타임 플러그인은 필요한 운영 능력을 타입이 있는 manifest로 선언하며, 문서와 런타임 manifest가 어긋나지 않는 계약 테스트를 둔다.

## 10. 인증과 세션 복구

### 10.1 목표

완전한 무인 로그인을 보장하지 않는다. 평소에는 세션을 자동 복원하고, 보안 인증이 필요한 순간에만 사용자가 개입하는 것을 목표로 한다.

### 10.2 우선순위

1. 공식 API 또는 제휴 토큰
2. 저장된 일반 브라우저 세션 재사용
3. 허용된 일반 로그인 폼 자동 제출
4. 사용자가 로그인한 일반 Chrome과 확장프로그램 연결
5. CAPTCHA, OTP, QR, 추가 인증만 사용자에게 요청
6. 공식 연동이 없으면 변경 준비 후 사용자 최종 확인 방식

### 10.3 세션 상태

- `unknown`
- `checking`
- `ready`
- `expired`
- `credential_required`
- `challenge_required`
- `credential_rejected`
- `locked_out_risk`
- `unsupported`
- `error`

### 10.4 재시도 차단

- 저장 자격 증명 거절 1회 후 자동 재시도를 중단한다.
- 사용자가 자격 증명을 갱신하기 전 같은 비밀번호를 다시 제출하지 않는다.
- CAPTCHA나 추가 인증은 실패로 반복하지 않고 `challenge_required`로 전환한다.
- 로그인 실패 원인과 마지막 시도 시각을 구조화해 저장한다.

### 10.5 보안

- 비밀번호는 Electron `safeStorage` 또는 OS 자격 증명 저장소로 암호화한다.
- 쿠키와 세션은 관리 브라우저 프로필에만 둔다.
- 백업, 로그, 스냅샷에 비밀번호·쿠키·인증 헤더를 포함하지 않는다.
- 탐지를 속이는 stealth·fingerprint 위장·보안 인증 우회를 제품 기반으로 사용하지 않는다.

자동화 연결 자체를 거절하는 사이트는 일반 Chrome 확장프로그램과 로컬 앱 연결을 우선 사용한다. 이 경로도 허용되지 않으면 공식 제휴 또는 사용자 승인형 반자동 흐름으로 낮춘다.

## 11. 백업·복원·인쇄

### 11.1 백업은 앱 설치와 분리한다

백업 기본 위치는 프로그램 설치 폴더나 Electron `userData` 내부만 사용하지 않는다. 사용자가 선택한 문서, 외장 드라이브, 클라우드 동기화 폴더에 저장할 수 있어야 한다.

### 11.2 백업 내용

- 스키마 버전과 생성 앱 버전
- 통합 메뉴와 가격 변형
- 논리 옵션과 연결
- 플랫폼 원본 식별자와 매핑
- 의도 규칙과 미해결 예외
- 정상 수집·반영 이력
- 이미지 원본과 파생본의 파일 또는 해시 참조
- 무결성 체크섬

다음은 포함하지 않는다.

- 아이디·비밀번호
- 쿠키·세션 토큰
- 인증 헤더
- 불필요한 개인정보가 포함된 원본 응답

### 11.3 자동 복구 지점

- 통합 메뉴 버전 1 확정 직후
- 대량 변경 실행 직전
- 플랫폼 반영 완료 후
- 메뉴 구조 또는 옵션 연결 변경 전
- 사용자가 수동 백업을 요청할 때

### 11.4 복원 방식

- 현재 데이터와 비교만 하기
- 선택 항목 병합 복원
- 통합 메뉴 전체 교체 복원

복원은 통합 메뉴를 되돌리는 작업이다. 플랫폼에 이미 반영된 변경은 별도의 역변경 계획과 재검증 없이는 자동으로 되돌리지 않는다.

### 11.5 사람이 읽는 출력

- PDF 또는 인쇄 화면: 카테고리, 메뉴, 변형 가격, 채널 가격, 옵션, 플랫폼 판매 여부
- CSV: 메뉴·가격·옵션 비교와 외부 검토
- 복구 패키지: 기계가 다시 읽을 수 있는 버전 JSON과 자산

## 12. 쓰기 안전성

각 쓰기 실행은 다음 단계를 거친다.

```text
최신 원본 재수집
  -> 외부 변경 검사
  -> 플랫폼별 변환
  -> 손실·미지원 검사
  -> 변경 계획 미리보기
  -> 실행 전 복구 스냅샷
  -> 플랫폼별 순차 적용
  -> 적용 직후 재수집
  -> 기대값 비교
  -> 성공·부분 실패 기록
```

- 같은 실행 키를 중복 적용하지 않도록 멱등 키를 둔다.
- 한 플랫폼 실패가 이미 성공한 다른 플랫폼을 자동 되돌리지 않는다.
- 실패한 항목만 재시도할 수 있어야 한다.
- 플랫폼이 반환한 성공 메시지만 믿지 않고 다시 읽은 값으로 성공을 확정한다.

## 14. 데이터 보존과 버전

- 통합 메뉴 변경은 증가하는 `canonicalVersion`을 가진다.
- 예외 후보는 입력 근거의 fingerprint를 가져 같은 상태를 중복 생성하지 않는다.
- 의도 규칙 변경과 사용은 감사 이력으로 남긴다.
- 원본 스냅샷과 정규화 데이터에는 출처 플랫폼, 수집 실행 ID, 확인 시각을 보존한다.
- 백업 스키마에는 독립적인 버전을 두고 구버전 복원용 마이그레이션을 제공한다.

## 15. 기존 구현에서 바꿔야 하는 지점

- `PLATFORM_METADATA.baemin.referenceCatalog = true` 전역 가정 제거
- `CatalogImportOrchestrator`의 수집 즉시 통합 메뉴 자동 생성 책임 분리
- `menus`를 활성 통합 카탈로그의 엔터티로 명시
- 초기 기준 선택과 버전 1 확정을 담당하는 bootstrap 서비스 추가
- 메뉴 매칭 점수를 설명 가능한 신호 묶음으로 확장
- 예외 후보와 의도 규칙 저장소 추가
- `PlatformAdapter`를 인증·읽기·투영·쓰기·검증 책임으로 단계적 분리
- 로그인 거절 회로 차단기와 세션 상태 저장 추가
- 백업·복원·인쇄 서비스를 메인 프로세스에 추가

## 17. 수용 기준

- 새 설치에서 플랫폼 수집만으로 통합 메뉴가 자동 확정되지 않는다.
- 사용자가 연결된 플랫폼 또는 빈 카탈로그를 초기 기준으로 선택할 수 있다.
- 통합 메뉴 버전 1 확정 이후 기준 플랫폼의 직접 변경도 외부 변경으로 탐지된다.
- 의도적으로 제외한 메뉴나 플랫폼별 가격 규칙을 다음 수집에서 다시 오류로 묻지 않는다.
- 옵션의 논리 통합이 플랫폼 원본 그룹을 자동 삭제하지 않는다.
- 불완전 수집, 손실 변환, 외부 충돌은 쓰기를 차단한다.
- 새 플랫폼은 핵심 엔진 변경 없이 플러그인 등록과 기능 제약 선언으로 추가할 수 있다.
- 로그인 거절 후 같은 자격 증명을 반복 제출하지 않는다.
- 통합 메뉴, 매핑, 의도 규칙을 외부 백업에서 복원할 수 있다.
- 출력 문서는 앱 없이도 메뉴·가격·옵션 구성을 확인할 수 있다.

## 18. 미룬 결정

다음은 실제 사용 범위가 생길 때 결정한다.

- 하나의 브랜드 정책을 여러 매장에 상속하는 방식
- 여러 사용자의 승인 권한과 감사 주체
- 가격 전략 추천에 주문·매출 데이터를 사용할지 여부
- 클라우드 백업 공급자와 자동 동기화
- 공식 제휴 API를 통한 주문·프로모션 통합 범위

미룬 결정은 Phase 1의 단일 매장 워크스페이스와 로컬 우선 구조를 깨지 않아야 한다.
