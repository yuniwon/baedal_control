# 배달앱 메뉴 동기화 삭제 반영 및 옵션 관리 설계서

- 작성일: 2026-04-13
- 대상 범위: 배민 우선 구현, 쿠팡이츠/땡겨요까지 확장 가능한 공통 구조
- 문서 목적: 플랫폼에서 사라진 메뉴/옵션 반영, 옵션 통합 기준 묶음, 대시보드 변경점 요약, 옵션 관리 탭을 구현하기 위한 제품/기술 기준 고정

## 1. 문제 정의

현재 앱은 배민 메뉴와 옵션을 읽어올 수 있지만, 플랫폼에서 직접 삭제된 항목을 앱 안에서 안정적으로 반영하지 못한다.  
또한 옵션은 메뉴 안의 부가 정보 수준으로만 보이며, 실제 운영에서 중요한 아래 문제를 독립적으로 관리할 수 없다.

1. 같은 옵션명과 같은 구성인데 연결 메뉴만 다른 옵션 그룹
2. 이름은 같지만 실제 옵션 구성이 다른 그룹
3. 플랫폼에서 더 이상 보이지 않는 옵션 그룹
4. 메뉴는 남아 있지만 특정 플랫폼에서만 연결이 끊긴 상태

이 문제를 해결하려면 `원본 플랫폼 데이터`, `앱 내부의 판단 상태`, `사용자에게 보여주는 관리 화면`을 분리해야 한다.

## 2. 이번 서브프로젝트의 한줄 정의

플랫폼에서 읽어온 메뉴/옵션 원본 스냅샷을 유지하면서, 누락 상태와 변경점을 추적하고, 옵션을 별도 탭에서 통합 기준 묶음으로 관리할 수 있게 한다.

## 3. 목표와 성공 기준

### 목표

- 플랫폼에서 직접 삭제되거나 사라진 메뉴/옵션을 앱에서 추적한다.
- 삭제 오탐을 줄이기 위해 누락 상태를 단계적으로 판정한다.
- 메뉴 관리와 옵션 관리를 분리해 복잡도를 낮춘다.
- 옵션을 메뉴별이 아니라 `실제로 같은 옵션인지` 기준으로 볼 수 있게 한다.
- 배민 우선 구현이지만 구조는 플랫폼 공통 모듈로 재사용 가능해야 한다.

### 성공 기준

- 가져오기 후 메뉴/옵션에 대해 `정상`, `누락 의심`, `플랫폼에 없음`, `재등장` 상태를 계산할 수 있다.
- 대시보드에서 이번 가져오기 변경점을 요약할 수 있다.
- 메뉴 관리에서 `플랫폼에 없음`과 `누락 의심`을 필터링할 수 있다.
- 옵션 관리 탭에서 `통합 기준 옵션 묶음`을 볼 수 있다.
- `플랫폼에 없음` 확정 시 해당 플랫폼의 활성 매핑이 제거된다.
- 모든 연결 플랫폼에서 없어졌을 때만 기준 메뉴가 자동 관리 제외된다.

## 4. 범위

### 포함

- 플랫폼 메뉴/옵션 원본 스냅샷 상태 확장
- 누락 상태 판정 로직
- 변경점 요약 생성
- 메뉴 관리의 삭제 관련 상태 표시
- 옵션 관리 탭 신설
- 옵션 통합 기준 묶음 계산
- 플랫폼 공통 서비스/모델 설계

### 제외

- 실제 배민 옵션 그룹 통합 반영
- 옵션 수정/재배선 자동 실행
- 옵션명/항목 편집 UI
- 자동 스케줄 재수집
- 여러 플랫폼의 옵션 반영 동시 실행

## 5. 제품 결정사항

### 5.1 상태 판정

메뉴와 옵션 모두 아래 공통 상태 머신을 사용한다.

- `present`
  - 이번 정상 수집에서 확인됨
- `missing_suspected`
  - 정상 수집 1회 누락
  - 아직 활성 매핑은 유지
- `absent_confirmed`
  - 정상 수집 2회 연속 누락
  - 이 시점에 해당 플랫폼 활성 매핑 제거
- `resurfaced`
  - 이전에 `missing_suspected` 또는 `absent_confirmed`였던 항목이 다시 보임

### 5.2 삭제 확정 기준

- 삭제 확정은 `정상 수집 2회 연속 누락`일 때만 한다.
- 수집 실패, 페이지 일부 누락, 옵션 탭 일부만 수집된 세션은 비교 기준으로 사용하지 않는다.

### 5.3 자동 관리 제외 규칙

- 특정 플랫폼에서만 `absent_confirmed`:
  - 해당 플랫폼 매핑만 제거
  - 기준 메뉴는 유지
- 모든 연결 플랫폼에서 `absent_confirmed`:
  - 기준 메뉴를 자동 `관리 제외`
- 자동 제외된 메뉴는 사용자가 `다시 포함`으로 복구 가능
- `resurfaced`는 자동 포함시키지 않고 상태만 표시

### 5.4 옵션 통합 기준

옵션 통합 기준 묶음의 키는 아래 값만 사용한다.

- 옵션 그룹명
- 최소 선택 수 / 최대 선택 수
- 옵션 항목 목록의 정규화 결과
  - 항목명
  - 항목 가격

연결 메뉴 목록은 묶음 계산 키에서 제외한다.  
즉, 연결 메뉴만 다른 경우 하나의 논리 묶음으로 본다.

### 5.5 기본 UI 노출 규칙

- 기본 화면에서 메뉴/옵션 ID는 숨긴다.
- ID는 내부 매칭, 진단 보기, 로그에만 사용한다.
- 사용자는 이름, 상태, 선택 규칙, 가격, 연결 메뉴, 변경점 중심으로 본다.

## 6. 아키텍처 원칙

이번 기능은 배민에 맞춰 구현하되, 하드코딩된 배민 전용 흐름으로 고정하지 않는다.  
공통 계층과 플랫폼 전용 계층을 아래처럼 분리한다.

### 공통 계층

- `CatalogImportOrchestrator`
  - 플랫폼 어댑터에서 메뉴/옵션 원본을 받아 저장
- `CatalogDiffService`
  - 직전 정상 수집 스냅샷과 비교해 변경점 계산
- `AbsenceStateService`
  - 누락 횟수와 상태 전이 관리
- `LogicalOptionGroupService`
  - 플랫폼 옵션 그룹을 공통 규칙으로 묶음 계산
- `ImportSummaryService`
  - 대시보드용 변경점 요약 생성

### 플랫폼 계층

- 각 플랫폼 어댑터는 공통 DTO를 반환한다.
- 배민 어댑터는 배민 API/DOM을 읽되, 결과는 메뉴/옵션 공통 스냅샷으로 변환한다.
- 쿠팡이츠/땡겨요는 나중에 같은 DTO를 채우기만 하면 된다.

즉, `배민에서 어떻게 읽는가`와 `앱이 그 데이터를 어떻게 판단하는가`를 분리한다.

## 7. 데이터 모델 설계

## 7.1 원본 메뉴 스냅샷

기존 `platform_menus`는 원본 메뉴 카탈로그를 유지하되, 상태 추적 컬럼을 추가한다.

- `last_seen_import_id`
- `last_seen_at`
- `missing_streak`
- `presence_status`
- `presence_changed_at`

`presence_status` 값은 `present | missing_suspected | absent_confirmed | resurfaced`

## 7.2 원본 옵션 스냅샷

기존 `platform_option_groups`를 확장한다.

- `last_seen_import_id`
- `last_seen_at`
- `missing_streak`
- `presence_status`
- `presence_changed_at`
- `signature_key`

`signature_key`는 옵션 통합 기준 계산용 정규화 키다.

## 7.3 플랫폼 가져오기 세션

새 테이블 `platform_import_runs`

- `import_run_id`
- `platform_code`
- `started_at`
- `finished_at`
- `status`
- `menu_fetch_completed`
- `option_fetch_completed`
- `summary_json`

이 테이블은 삭제 오탐 방지를 위해 필요하다.  
메뉴와 옵션 수집이 모두 정상 완료된 세션만 비교 기준으로 사용한다.

## 7.4 변경점 기록

새 테이블 `platform_import_changes`

- `change_id`
- `import_run_id`
- `platform_code`
- `entity_type` (`menu`, `option_group`)
- `entity_key`
- `change_type`
- `before_json`
- `after_json`

`change_type` 예:

- `created`
- `missing_suspected`
- `absent_confirmed`
- `resurfaced`
- `name_changed`
- `price_changed`
- `option_signature_changed`

## 7.5 논리 옵션 묶음

논리 옵션 묶음은 우선 계산 기반으로 처리한다.  
초기 단계에서는 별도 영구 테이블 없이 서비스에서 계산해 렌더러에 전달해도 된다.

필요 시 후속 단계에서 캐시 테이블로 분리한다.

## 8. 가져오기와 비교 흐름

### 8.1 정상 가져오기

1. 플랫폼 어댑터가 메뉴 원본을 읽는다.
2. 플랫폼 어댑터가 옵션 원본을 읽는다.
3. 두 수집이 모두 성공하면 `platform_import_runs`를 `completed`로 마감한다.
4. 이번 스냅샷을 저장한다.
5. 직전 `completed` 세션과 비교한다.
6. 메뉴/옵션별 변경점을 계산한다.
7. 누락 횟수와 상태를 갱신한다.
8. 대시보드 요약을 생성한다.

### 8.2 부분 실패 가져오기

- 메뉴 또는 옵션 중 하나라도 실패하면 `partial_failed`
- 이 세션은 삭제 확정 비교 기준으로 사용하지 않는다.
- 사용자에게는 가져오기 실패와 함께 기존 상태를 유지했다고 안내한다.

### 8.3 누락 처리

- 직전 정상 세션에 있었고 이번 정상 세션에 없는 항목:
  - `missing_streak += 1`
- `missing_streak == 1`
  - `missing_suspected`
- `missing_streak >= 2`
  - `absent_confirmed`

### 8.4 재등장 처리

- 이전 상태가 `missing_suspected` 또는 `absent_confirmed`
- 이번 정상 세션에서 다시 보이면
  - `missing_streak = 0`
  - `presence_status = resurfaced`

## 9. 매핑 처리 규칙

### 9.1 메뉴

- 메뉴가 `absent_confirmed`가 되면 해당 플랫폼 매핑을 활성 연결에서 제거한다.
- 단, 매핑 삭제는 물리 삭제 대신 상태 기반 비활성화가 더 적합하다.
- 초기 단계에서는 기존 매핑 테이블을 유지하면서, `platform_menu_id`가 더 이상 현재 카탈로그에 존재하지 않는 경우 렌더러/미리보기에서 비활성으로 해석해도 된다.
- 후속 단계에서는 `mapping_status` 컬럼을 추가해 `active | source_absent`로 관리한다.

### 9.2 옵션

- 옵션은 아직 반영 엔진과 직접 연결되지 않으므로 상태만 관리한다.
- 후속 옵션 통합/재배선 기능에서 `absent_confirmed`와 `resurfaced` 정보를 그대로 사용한다.

## 10. 옵션 관리 탭 설계

### 10.1 기본 구조

좌측 내비게이션에 `옵션 관리` 탭을 추가한다.

기본 목록은 `통합 기준 옵션 묶음`이다.

각 행에는 아래 정보를 보여준다.

- 대표 옵션명
- 선택 규칙
- 옵션 항목 수
- 연결 메뉴 수
- 원본 그룹 수
- 상태

### 10.2 상태 배지

- `통합 가능`
  - 같은 시그니처를 가진 원본 그룹이 2개 이상
- `구성 다름`
  - 이름은 같지만 시그니처가 다름
- `누락 의심`
- `플랫폼에 없음`
- `재등장`

### 10.3 펼침 상세

행을 펼치면 아래를 보여준다.

- 연결 메뉴 목록
- 원본 플랫폼 그룹 목록
- 마지막 확인 시각
- 최근 상태 변화

ID는 기본 숨김이며, 필요 시 진단 모드에서만 보여준다.

## 11. 메뉴 관리 화면 설계 변경

### 11.1 메뉴 상태

메뉴 관리에는 아래 상태를 추가한다.

- `누락 의심`
- `플랫폼에 없음`
- `재등장`
- `자동 제외됨`

### 11.2 필터

- 전체
- 관리 대상
- 관리 제외
- 가게 연결 검토 필요
- 누락 의심
- 플랫폼에 없음

### 11.3 플랫폼에 없음 표시

기본 원본 정보 카드에는 ID 대신 아래를 보여준다.

- 어느 플랫폼에서 사라졌는지
- 마지막 확인 시각
- 활성 매핑 해제 여부
- 재매핑이 필요한지 여부

## 12. 대시보드 설계 변경

대시보드 상단에 `이번 가져오기 변경점` 요약 카드를 추가한다.

예시 항목:

- 새 메뉴
- 누락 의심 메뉴
- 플랫폼에 없음 확정 메뉴
- 새 옵션 묶음
- 통합 가능 옵션 묶음
- 재등장 항목

대시보드는 요약만 보여주고, 상세 확인은 메뉴 관리 / 옵션 관리로 이동한다.

## 13. 플랫폼 공통 인터페이스

각 플랫폼 어댑터는 아래 DTO를 반환할 수 있어야 한다.

### 메뉴 원본 DTO

- `platformCode`
- `sourceId`
- `sourceName`
- `groupName`
- `status`
- `priceSummary`
- `bindingSummary`
- `rawPayload?`

### 옵션 원본 DTO

- `platformCode`
- `sourceId`
- `sourceName`
- `minSelect`
- `maxSelect`
- `items[]`
  - `name`
  - `price`
  - `status?`
- `linkedMenus[]`
  - `sourceMenuId`
  - `sourceMenuName`
  - `groupName?`
- `rawPayload?`

플랫폼별 특수 필드는 `rawPayload`에 남기고, 비교/상태/UI는 공통 필드만 사용한다.

## 14. 정규화 규칙

옵션 묶음 계산과 변경점 비교 시 아래 정규화를 사용한다.

- 이름: trim, 연속 공백 축소
- 가격: 정수 값 사용
- 항목 순서: 이름 + 가격 기준 정렬 후 비교
- 운영 상태(`품절`, `재판매 시각`)는 통합 키에서 제외

운영 상태는 UI 참고 정보로만 사용하고, 같은 옵션 여부 판단에는 쓰지 않는다.

## 15. 오류 처리와 보호장치

- 메뉴 수집만 성공하고 옵션 수집이 실패한 세션은 삭제 비교에 사용하지 않는다.
- 옵션 탭 전체를 다 읽지 못한 경우 `option_fetch_completed = false`
- 이 경우 옵션 누락 상태는 갱신하지 않는다.
- 사용자의 수동 판단(관리 제외, 수동 매핑, 후속 통합 무시)은 자동 수집이 덮어쓰지 않는다.

## 16. 테스트 전략

### 단위 테스트

- 누락 상태 전이
- 재등장 처리
- 옵션 시그니처 계산
- 통합 기준 옵션 묶음 생성
- 모든 플랫폼 부재 시 자동 관리 제외 조건

### 저장소 테스트

- 플랫폼 스냅샷 상태 컬럼 저장/조회
- 가져오기 세션 저장
- 변경점 저장

### 렌더러 테스트

- 대시보드 변경점 요약
- 메뉴 관리의 `플랫폼에 없음` 필터
- 옵션 관리의 통합 기준 묶음 표시
- ID 기본 숨김

### 실제 검증

- 배민에서 메뉴/옵션 수집
- 1회 누락 시 `누락 의심`
- 2회 연속 누락 시 `플랫폼에 없음`
- 재등장 시 상태 변경

## 17. 리스크와 대응

### 리스크 1: 수집 불완전으로 인한 대량 삭제 오탐

- 대응: 정상 완료 세션만 삭제 비교 기준으로 사용

### 리스크 2: 같은 이름인데 실제 구성 다른 옵션 오통합

- 대응: 이름만이 아니라 선택 규칙과 항목 구성까지 비교

### 리스크 3: 특정 플랫폼 삭제가 전체 메뉴 정지를 유발

- 대응: 모든 연결 플랫폼이 사라졌을 때만 자동 관리 제외

### 리스크 4: UI 과복잡화

- 대응: 메뉴와 옵션을 별도 탭으로 분리, 기본 화면에서 ID 숨김
