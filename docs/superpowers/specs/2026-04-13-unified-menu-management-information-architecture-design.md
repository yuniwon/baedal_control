# 통합 메뉴 관리 관점 정보구조 재정의

- 작성일: 2026-04-13
- 문서 목적: 현재 앱을 `동기화 도구`가 아니라 `통합 메뉴 관리 워크스페이스`로 해석하기 위한 제품/정보구조 기준을 고정한다.
- 대상 독자: 현재 프로젝트를 수정하거나 검수하는 에이전트, 이후 UI/기능 작업을 이어받는 개발자
- 적용 범위: 제품 포지셔닝, 화면 정보구조, 용어, 우선순위 판단 기준

## 1. 배경

현재 구현은 `계정 저장 -> 메뉴 수집 -> 매핑 검토 -> 반영 미리보기 -> 실행 기록` 흐름이 강하다.  
이건 잘못된 방향이 아니라, 실수 비용이 큰 배달 플랫폼 반영 작업에서 가장 위험한 구간을 먼저 구현한 결과다.

하지만 제품의 상위 목표는 여기에 머물지 않는다.

이 프로젝트의 본래 목표는 다음이다.

1. 여러 배달 플랫폼에 파편화된 메뉴 상태를 한곳에서 확인한다.
2. 가게 기준 메뉴를 한 체계로 관리한다.
3. 플랫폼별 차이와 예외를 비교하면서 수정한다.
4. 반영 전 검수와 실행 기록까지 같은 작업 공간 안에서 처리한다.

즉, 이 앱은 장기적으로 `멀티플랫폼 메뉴 운영 워크스페이스`가 되어야 한다.

## 2. 제품 한줄 정의

배민, 쿠팡이츠, 땡겨요 등에 흩어진 메뉴 운영을 하나의 기준 메뉴 체계로 통합해 확인, 수정, 검수, 반영할 수 있게 하는 로컬 데스크톱 워크스페이스

## 3. 이 제품이 무엇이고 무엇이 아닌가

### 이것이다

- 기준 메뉴를 중심으로 여러 플랫폼 상태를 통합 관리하는 운영 도구
- 반영 전에 차이, 연결 상태, 누락, 예외를 검수하는 작업 공간
- 실행 이후까지 기록과 실패 원인을 추적하는 로컬 퍼스트 콘솔

### 이것은 아니다

- 소비자용 배달앱 UI
- 단순 메뉴 CRUD 폼
- 플랫폼 메뉴를 무조건 일괄 반영하는 자동화 버튼 모음
- 마케팅 사이트나 브랜드 쇼케이스

## 4. 고려한 정보구조 접근

### 접근 A. 현재처럼 기능별 탭을 더 다듬는다

- 구조: 대시보드 / 메뉴 / 옵션 / 매핑 / 설정 / 기록
- 장점: 기존 구조와 가장 가깝고 구현 리스크가 낮다.
- 단점: 사용자가 `한곳에서 통합 관리한다`는 감각을 받기 어렵다. 메뉴 수정, 연결 검토, 반영 준비가 서로 다른 화면으로 찢어진다.

### 접근 B. 기준 메뉴 중심 워크스페이스로 재구성한다

- 구조: 개요 / 메뉴 워크스페이스 / 옵션 / 플랫폼 연결 / 활동 기록
- 장점: 제품 비전과 가장 잘 맞는다. 메뉴 한 행 또는 한 상세 패널 안에서 기준값, 플랫폼 상태, 연결, 검토 필요 상태를 함께 다룰 수 있다.
- 단점: 현재 별도 페이지인 매핑 검토 기능을 점진적으로 흡수해야 하므로 정보구조 설계가 필요하다.

### 접근 C. 플랫폼 중심 운영 화면으로 재구성한다

- 구조: 배민 / 쿠팡이츠 / 땡겨요 / 공통 설정 / 기록
- 장점: 플랫폼별 장애 대응이나 DOM 이슈 추적에는 직관적이다.
- 단점: 기준 메뉴 중심 편집과 통합 관리라는 제품 핵심이 약해진다. 결국 다시 기준 메뉴 관점의 화면이 필요해진다.

### 권장안

접근 B를 기준으로 삼는다.

이 프로젝트의 핵심은 특정 플랫폼을 잘 조작하는 것이 아니라, `가게 기준 메뉴`를 중심으로 플랫폼 상태를 통합하는 데 있다.  
따라서 정보구조도 플랫폼이 아니라 기준 메뉴를 중심에 둬야 한다.

## 5. 권장 정보구조

### 5.1 최상위 내비게이션

#### 1) 개요

- 오늘 확인해야 할 위험과 상태를 요약한다.
- 플랫폼 연결 상태
- 최근 가져오기 결과
- 검토 필요 항목 수
- 반영 예정 항목 수
- 최근 실행 결과

이 화면의 역할은 `무엇이 문제인가`와 `어디서부터 처리해야 하는가`를 알려주는 것이다.

#### 2) 메뉴 워크스페이스

- 제품의 중심 화면이다.
- 기준 메뉴 목록이 주 화면이 된다.
- 각 메뉴는 단순 이름/가격 행이 아니라, 플랫폼 상태를 품은 작업 단위여야 한다.

한 메뉴를 기준으로 최소한 아래 정보가 연결돼야 한다.

- 기준 메뉴명 / 기준 가격
- 관리 대상 여부
- 연결된 플랫폼 수
- 플랫폼별 현재 메뉴명 / 가격 / 상태
- 연결 검토 필요 여부
- 원본 누락 의심 / 플랫폼에 없음 / 재등장 상태
- 반영 예정 변경
- 관련 옵션 묶음

현재 별도 탭인 `매핑 검토`는 장기적으로 이 화면의 하위 모드나 상세 패널로 들어가는 것이 맞다.

#### 3) 옵션

- 옵션은 메뉴와 밀접하지만 별도 복잡도를 가진다.
- 따라서 독립 최상위 화면은 유지할 수 있다.
- 다만 이 화면도 `플랫폼 옵션 수집 결과를 보여주는 페이지`가 아니라 `기준 메뉴 운영을 보조하는 옵션 정리 공간`이어야 한다.

핵심 과업은 아래에 집중한다.

- 같은 구성의 옵션 묶음 통합 가능 여부 검토
- 이름은 같지만 구성이 다른 옵션 충돌 확인
- 원본 누락 / 재등장 상태 점검
- 어떤 메뉴들이 이 옵션과 연결돼 있는지 확인

#### 4) 플랫폼 연결

- 현재의 `설정`보다 더 정확한 이름은 `플랫폼 연결`이다.
- 이 화면의 역할은 앱 전역 설정이 아니라 커넥터 운영이다.

다뤄야 할 내용은 아래다.

- 플랫폼 계정 저장
- 연결 상태 확인
- 수집 재실행
- 수집 검사 정보
- 최근 실패 원인

#### 5) 활동 기록

- 현재의 `실행 기록`을 확장한 개념이다.
- 가져오기 기록과 반영 기록을 함께 다룬다.
- 사용 목적은 감사 로그보다는 운영 추적이다.

여기서 중요한 것은:

- 무엇을 가져왔는가
- 어떤 변화가 감지되었는가
- 무엇을 반영했는가
- 무엇이 실패했는가
- 어떤 항목이 계속 검토 대상으로 남는가

## 6. 핵심 작업 단위

이 프로젝트를 이해할 때 에이전트는 아래 여섯 가지를 핵심 단위로 봐야 한다.

### 기준 메뉴

운영자가 직접 책임지는 기준값이다.  
이 앱에서 가장 중요한 객체이며, 다른 데이터는 결국 여기에 연결된다.

### 플랫폼 메뉴 스냅샷

각 플랫폼에서 읽어온 현재 상태다.  
기준 메뉴를 대체하는 데이터가 아니라, 비교와 검수의 대상이다.

### 매핑

기준 메뉴와 플랫폼 메뉴가 어떻게 연결되는지 나타내는 링크다.  
이 제품에서 매핑은 별도 기능이라기보다 통합 관리의 일부다.

### 논리 옵션 묶음

옵션을 플랫폼 원본 단위로만 보지 않고, 운영자가 이해할 수 있는 묶음으로 재구성한 객체다.

### 검토 필요 상태

`missing_mapping`, `binding_review`, `source_missing_review`, `price_variant_review` 같은 상태는 부가 정보가 아니다.  
이 워크스페이스에서 실제로 사람이 결정을 내려야 하는 작업 큐다.

### 실행 이력

반영은 결과가 남아야 한다.  
이력은 단순 로그가 아니라 신뢰를 만드는 근거다.

## 7. 화면별 역할 재정의

현재 화면을 앞으로 어떤 성격으로 다뤄야 하는지 정리하면 아래와 같다.

### DashboardPage

- 현재 역할: 요약 대시보드
- 앞으로의 역할: `운영 개요`
- 판단 기준: 오늘 처리할 위험과 변화량을 빠르게 훑는 첫 화면

### MenuPage

- 현재 역할: 기준 메뉴 편집
- 앞으로의 역할: `통합 메뉴 워크스페이스`
- 판단 기준: 기준값 편집, 플랫폼 비교, 상태 확인, 예외 진입의 중심 화면

### MappingPage

- 현재 역할: 별도 매핑 검토
- 앞으로의 역할: 메뉴 워크스페이스 내부의 연결 관리 모드
- 판단 기준: 장기적으로는 독립된 세계가 아니라 메뉴 상세 작업의 일부

### OptionPage

- 현재 역할: 읽기 중심 옵션 묶음 확인
- 앞으로의 역할: `옵션 정리 워크스페이스`
- 판단 기준: 메뉴 운영을 보조하는 정합성 관리 화면

### SettingsPage

- 현재 역할: 계정/수집/검사
- 앞으로의 역할: `플랫폼 연결`
- 판단 기준: 전역 설정이 아니라 커넥터 상태와 진단을 다루는 화면

### HistoryPage

- 현재 역할: 실행 기록 열람
- 앞으로의 역할: `활동 기록`
- 판단 기준: 가져오기와 반영을 함께 보는 운영 추적 화면

## 8. 용어 기준

에이전트가 이후 UI 문구와 문서를 다룰 때는 아래 표현을 우선한다.

- `기준 메뉴`: 앱이 책임지는 원본 값
- `플랫폼 메뉴`: 각 배달 플랫폼에서 읽어온 값
- `연결`: 기준 메뉴와 플랫폼 메뉴의 관계
- `검토 필요`: 사람이 판단해야 해서 자동 실행 대상에서 빠진 상태
- `반영 예정`: 실행 가능한 변경
- `플랫폼 연결`: 계정/커넥터/수집 관리 화면
- `활동 기록`: 가져오기 + 반영 기록

가능하면 피할 표현은 아래다.

- `동기화 툴`
- `자동화 프로그램`
- `매핑 페이지`
- `설정 페이지`

이 표현들은 제품의 상위 목적보다 구현 수단을 더 강하게 보이게 만든다.

## 9. 디자인 톤 가이드

이 문서는 시각 디자인 문서가 아니지만, 정보구조와 연결되는 톤 기준은 남겨둔다.

- 1차 레퍼런스: `supabase`
- 2차 레퍼런스: `linear.app`

해석 기준:

- `supabase`에서 가져올 것
  - 데이터 밀도가 있는 운영 콘솔 감각
  - 상태 배지와 기술적 작업감
  - 대시보드와 리스트의 차분한 구조

- `linear.app`에서 가져올 것
  - 정보 위계의 정리감
  - 과한 카드 장식 없이 집중되는 작업 화면
  - 한 워크스페이스 안에서 흐름이 이어지는 느낌

피해야 할 방향:

- 소비자용 배달앱처럼 보이는 비주얼
- 화려한 마케팅 랜딩 스타일
- 매핑/설정/기록을 각각 따로 노는 툴처럼 보이게 하는 분절된 UI

## 10. 에이전트 작업 원칙

이 프로젝트를 수정하는 에이전트는 아래 기준으로 판단한다.

1. 새 UI를 추가할 때는 `기준 메뉴를 중심으로 플랫폼 상태를 더 잘 이해하고 관리하게 만드는가`를 먼저 본다.
2. 새로운 예외 상태나 검토 흐름을 추가하더라도, 가능하면 메뉴 워크스페이스 안에서 이어지게 한다.
3. 별도 페이지를 늘리기보다, 기존 작업 흐름 안에 패널/섹션/서브모드로 흡수할 수 있는지 먼저 검토한다.
4. 내부 ID나 구현 세부정보보다 운영자가 내릴 결정과 상태를 먼저 보여준다.
5. 자동 실행보다 검수 가능성, 추적 가능성, 실패 설명 가능성을 우선한다.
6. 현재 구현이 `검수/반영 콘솔` 성격을 띠더라도, 제품 전체는 `통합 메뉴 관리 워크스페이스`라는 해석을 유지한다.

## 11. 당장 바꾸지 않는 것

이 문서는 즉시 코드 구조를 뒤엎으라는 뜻이 아니다.

당장은 아래를 유지해도 된다.

- 옵션 관리의 별도 화면
- 가져오기와 반영 기록의 분리 저장 구조
- 수집/매핑/반영을 단계별로 나눈 내부 서비스 구조

대신, 앞으로의 UI/정보구조 판단에서 이 문서를 상위 기준으로 삼는다.

## 12. 최종 정리

현재 프로젝트는 구현상 `멀티플랫폼 메뉴 검수/동기화 콘솔`의 형태를 띠고 있지만,  
제품 의도와 앞으로의 정보구조는 `통합 메뉴 관리 워크스페이스`로 잡는 것이 맞다.

이 차이를 명확히 구분해야 앞으로 다음 두 가지를 동시에 만족시킬 수 있다.

1. 배달 플랫폼 반영의 위험을 계속 통제한다.
2. 사용자가 정말로 `한곳에서 메뉴를 관리한다`는 느낌을 받게 만든다.
