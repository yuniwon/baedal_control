## 기존 main에서 유지할 제품 아이디어

### 1. 통합 관리 범위

기존 PRD는 단순 가격 수정기가 아니라 아래 범위를 하나의 통합 카탈로그로 보았다.

- 메뉴명, 가격, 판매중/품절
- 옵션 그룹, 옵션 항목, 옵션 가격
- 영업중지/재개
- 영업시간/브레이크타임
- 플랫폼별 차이 비교
- 역방향 수집 후 승인 머지
- 작업 이력과 감사 로그

현재 Electron 앱은 메뉴/옵션/매핑/부재 감지까지 많이 왔고, 여기서 이어서 붙일 다음 범위로는 아래가 유효하다.

- 영업중지/재개 통합 관리
- 영업시간 통합 관리
- 플랫폼에서 직접 바뀐 값의 역수집과 승인 반영
- 작업 결과 증빙 강화(스크린샷, 재조회 결과, 실패 사유)

### 2. 통합 도메인 모델

기존 Python 시뮬레이터의 핵심 도메인 모델은 지금도 유효하다.

- `Store`, `StoreBinding`
- `Category`
- `Item`
- `OptionGroup`, `Option`
- `OperatingHours`
- `Inventory`
- `StoreState`
- `AuditLog`
- `PlatformSnapshot`
- `UnifiedDelta`

Electron 앱 기준으로 보면 다음처럼 매핑하면 된다.

- 현재 `기준 메뉴 / 플랫폼 메뉴 / 매핑` 구조 -> `Item`, `ItemMapping`
- 현재 옵션 수집/매핑 구조 -> `OptionGroup`, `Option`
- 현재 계정 연결 -> `StoreBinding`
- 앞으로 들어갈 영업중지/영업시간 -> `StoreState`, `OperatingHours`
- 실행 기록 -> `AuditLog`

즉, 기존 main의 가장 큰 자산은 기능 구현체가 아니라 "어떤 데이터를 기준 모델로 삼을지"에 대한 정리다.

## 기존 main에서 유지할 기술 아이디어

### 1. 동기화 파이프라인 단계화

기존 PRD의 파이프라인은 지금 Electron 앱에도 그대로 적용할 가치가 있다.

1. 편집
2. 검증
3. 플랫폼별 적용 계획 생성
4. 실제 반영
5. 저장 결과 검증
6. 재조회 후 불일치 확인
7. 로그 기록

지금 앱은 일부 단계가 이미 있지만, 앞으로는 모든 쓰기 작업을 이 단계로 통일하는 것이 좋다.

- 메뉴 가격 수정
- 메뉴 숨김/노출
- 옵션 가격 수정
- 메뉴 추가/삭제
- 영업중지/영업시간 변경

### 2. 플랫폼 제약 미리보기 규칙

기존 Python 시뮬레이터에는 플랫폼별 `preview.rules.json` 개념이 있었다. 이건 Electron 앱에서 매우 유용하다.

예시:

- 메뉴명 최대 길이
- 설명 최대 길이
- 가격 최소값/증감 단위
- 옵션 그룹 최대 개수
- 옵션 항목 최대 개수
- 이미지 제약

이 규칙은 지금 구조에 그대로 옮길 수 있다.

- `src/shared/platform-preview-rules.ts` 또는 JSON
- 저장 전 경고/차단
- 플랫폼별 "왜 이 값이 안 되는지"를 사용자 문구로 바로 안내

이건 하드코딩 대신 범용 모듈로 빼야 하고, 이후 배민/쿠팡이츠/땡겨요 전부 같은 방식으로 재사용 가능하다.

### 3. 버전드 셀렉터 맵

기존 PRD2의 핵심은 "셀렉터를 코드에 박지 말고 버전 데이터로 관리하자"였다.

남길 포인트:

- 플랫폼별 셀렉터 맵 파일 분리
- 버전 정보 명시
- 변경 시 롤백 가능
- 로그인/목록/상세/저장/토스트/모달 등 영역별로 나눔

Electron 앱에서도 이 방향은 맞다.  
특히 현재처럼 플랫폼별로 화면 구조가 계속 달라질 수 있는 상황에서는 다음 구조가 필요하다.

- 읽기 셀렉터
- 쓰기 셀렉터
- 성공 판별 셀렉터
- 방해 요소(토스트/팝업/배너) dismiss 셀렉터

### 4. 에러 코드 사전

기존 PRD2에는 에러를 문자열이 아니라 코드 체계로 관리하려는 설계가 있었다.

예:

- `AUTH_INVALID`
- `AUTH_2FA_REQUIRED`
- `CAPTCHA_BLOCKED`
- `SELECTOR_MISSING`
- `ELEMENT_NOT_INTERACTABLE`
- `TOAST_ERROR`
- `RATE_LIMIT`
- `TIMEOUT`
- `VALIDATION_FAIL`
- `PARTIAL_APPLY`
- `SNAPSHOT_MISMATCH`

이건 지금 Electron 앱에도 꼭 필요하다.

이유:

- 실행 기록을 사람이 읽기 쉽게 묶을 수 있음
- 자동 재시도 가능/불가능을 구분할 수 있음
- UI에서 사용자 안내 문구를 일관되게 보여줄 수 있음
- 플랫폼별 실패 패턴을 통계화할 수 있음

권장 후속 작업:

- `src/shared/platform-error-codes.ts`
- 에러 코드별 사용자 문구, 로그 문구, 재시도 정책 분리

### 5. 증빙 기반 검증

기존 main은 "저장 버튼 클릭" 자체보다 "정말 반영되었는지"를 더 중요하게 봤다.

남겨야 할 기준:

- 저장 성공 토스트 확인
- 저장 후 DOM 재조회
- 필요시 스크린샷 저장
- 불일치면 `SNAPSHOT_MISMATCH`로 기록

이 방향은 현재 배민 자동화 고도화에도 그대로 필요하다.

### 6. 모의 포털 / 파일백드 커넥터

Python 시뮬레이터는 실제 포털 대신 JSON 상태를 써서 커넥터 흐름을 검증했다.

이 아이디어는 Electron 앱에서도 테스트용으로 가치가 있다.

- 실제 운영 사이트에 접속하지 않아도 회귀 테스트 가능
- 메뉴/옵션/품절/삭제/부재 감지 시나리오를 고정 데이터로 검증 가능
- 플랫폼 DOM이 흔들릴 때도 오케스트레이션 계층 테스트를 분리할 수 있음

즉, Python 구현을 유지할 필요는 없지만 "모의 플랫폼 계층" 개념은 유지하는 편이 좋다.

## 지금 Electron 앱 기준 추천 이관 우선순위

### 우선순위 A

- 플랫폼 preview rules 모듈화
- 공통 에러 코드/실행 상태 코드 정리
- 쓰기 결과 검증 규칙 통일
- 실행 기록에 에러 코드/증빙 연결

### 우선순위 B

- 영업중지/재개 도메인 추가
- 영업시간 도메인 추가
- 플랫폼별 쓰기 오케스트레이터 공통 인터페이스 정리

### 우선순위 C

- 역방향 동기화 승인 플로우
- 모의 포털 테스트 하네스
- 셀렉터 버전 관리/헬스체크 도구

## 구현 관점에서 바로 쓸 수 있는 설계 메모

### 1. 공통 플랫폼 모듈

각 플랫폼 구현은 아래 추상화 위에 얹는 편이 좋다.

- 인증
- 목록 수집
- 상세 수집
- 변경 계획 생성
- 변경 적용
- 반영 검증
- 결과 기록

즉, "플랫폼별 함수 모음"이 아니라 "같은 생명주기를 가진 어댑터" 구조로 유지해야 한다.

### 2. 메뉴/옵션을 별도 탭으로 운영하는 현재 UI 방향은 맞다

기존 PRD도 메뉴와 옵션을 분리 가능한 도메인으로 봤다.  
지금 Electron 앱에서 메뉴 탭과 옵션 탭을 분리하는 방향은 확장성 측면에서 맞다.

이 구조의 장점:

- 옵션 중복 병합 대응이 쉬움
- 옵션만 따로 플랫폼별 제약 검증 가능
- 메뉴 추가/삭제와 옵션 수정 흐름을 분리 가능

### 3. 부재 감지는 "즉시 삭제"보다 "후보 상태 표시"가 맞다

기존 PRD의 reconcile 관점과도 맞는다.

권장 상태:

- 1회 누락: 경고
- 2회 연속 누락: 제거 후보
- 사용자 확인 후 매핑 제거
- 메뉴 관리에서는 "플랫폼에 없음" 상태를 유지 표시

이 원칙은 메뉴와 옵션 모두에 공통 적용 가능하다.
